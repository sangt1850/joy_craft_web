JoyCraft — 인터랙티브 참여형 사이트 플랫폼 기획 정리
1. 프로젝트 개요
   미리캔버스/PPT처럼 "컴포넌트 단위 슬라이드"를 이어 붙여서, 사용자가 직접 조작하며 참여하는 인터랙티브 웹사이트를 만드는 플랫폼. 생일·연인·가족 등 이벤트성 선물로 주고받는 용도를 우선 타겟으로 한다.

프로젝트명: JoyCraft

예시 컴포넌트:

질문 + 예/아니오 버튼. "아니오"는 커서가 다가가면 도망가서 절대 누를 수 없음
클릭 시 화려하게 펼쳐지는 꽃다발 애니메이션
클릭하면 열리는 편지지
2. 역할 정의
   역할
   설명
   MASTER
   플랫폼 자체를 만드는 개발자 (본인). SDK, 컴포넌트 레지스트리, 노코드 빌더, 렌더러 개발
   CREATOR (=EDITOR)
   개별 컴포넌트를 만드는 사람. 코드 가능한 사람은 SDK로 신규 컴포넌트 개발, 코드 못하는 사람은 노코드 빌더로 기존 컴포넌트의 프리셋(템플릿) 제작
   CUSTOMER
   만들어진 컴포넌트들을 조합해서 최종 사이트를 만드는 사람. 순서 배치 + 텍스트/이미지/색상/폰트 커스텀

3. 데이터 모델
   3계층 구조
   Component Type (MASTER/개발자 CREATOR가 코드로 정의) — 실제 로직 + customization schema
   Component Template (CREATOR의 산출물) — Component Type에 기본값을 채운 완성된 프리셋
   Site Instance (CUSTOMER의 산출물) — 템플릿을 순서대로 배치하고 override 값을 채운 최종 결과물
   ERD
   USERS ||--o{ COMPONENT_TEMPLATES : creates

USERS ||--o{ SITES : owns

COMPONENT_TYPES ||--o{ COMPONENT_TEMPLATES : "instantiated as"

COMPONENT_TEMPLATES ||--o{ SITE_SLIDES : "used in"

SITES ||--o{ SITE_SLIDES : contains

SITES ||--o{ ASSETS : uploads

USERS { uuid id PK, string role, string email }

COMPONENT_TYPES { string id PK, string name, jsonb schema, string component_ref, string platformMode }

COMPONENT_TEMPLATES { uuid id PK, string component_type_id FK, uuid creator_id FK, jsonb default_values, int version, string status }

SITES { uuid id PK, uuid customer_id FK, string title, string status }

SITE_SLIDES { uuid id PK, uuid site_id FK, int order_index, uuid template_id FK, int template_version, jsonb overrides }

ASSETS { uuid id PK, uuid owner_id FK, string url, string type }
핵심 설계 원칙
컴포넌트 로직(코드)과 데이터(값)를 완전히 분리. DB에는 코드가 아니라 메타데이터·스키마·값만 저장.
template_version을 site_slides에 고정(pin). CREATOR가 템플릿을 업데이트해도 이미 만들어진 CUSTOMER 사이트는 깨지지 않음.
jsonb로 유연한 커스터마이즈 필드 저장. 컴포넌트마다 스키마가 다르므로 고정 컬럼 대신 jsonb 사용.
4. 컴포넌트 스키마: customization + platformMode
   {

"id": "yes-no-chase-button",

"component": "YesNoChaseButton",

"platformMode": "responsive",

"schema": {

    "questionText": { "type": "string", "label": "질문 문구" },

    "yesButtonColor": { "type": "color" },

    "noButtonSpeed": { "type": "number", "min": 0.5, "max": 3, "default": 1.5 },

    "fontFamily": { "type": "font" }

}

}

platformMode 값:

responsive (기본) — 상대 단위/breakpoint로 모바일·웹 모두 대응. 마우스 전용 인터랙션은 터치 대체 로직 필수 (예: 탭 시 순간이동)
mobile-only — 터치/자이로 등 모바일 전용 인터랙션
web-only — 마우스 호버 등 큰 화면 전제
webapp-only — PWA(설치형)·앱 전용 기능(진동, 공유 시트 등)

렌더러는 접속 환경을 감지해 platformMode와 안 맞으면 대체 화면을 보여줘야 함. CUSTOMER 에디터에서도 컴포넌트에 플랫폼 배지를 표시해 미스매치를 사전 안내.

React Native/Flutter 대신 Capacitor를 택한 이유: 이 플랫폼의 핵심은 컴포넌트의 커스텀 애니메이션 자체이며, 네이티브 프레임워크로 가면 CREATOR SDK를 플랫폼별로 두 벌 만들어야 함. Capacitor는 하나의 웹 코드베이스로 웹/PWA/앱을 모두 커버.

iptime NAS2dual — Docker 미지원 모델. SMB/NFS 공유 폴더로만 사용, RAID1 이중화. 미니PC가 NFS로 마운트해와 MinIO 데이터 경로로 지정 (실제 파일은 NAS에 적재, API는 S3 인터페이스로 접근)
6. 인프라 구성 (비용 최소화)
   미니PC: Docker Compose로 Postgres + Spring Boot + MinIO 구동 (실질적 서버 역할)
   NAS: 순수 저장소, RAID1
   외부 노출: Cloudflare Tunnel (무료, 포트포워딩/공인IP 불필요, HTTPS 자동)

services:

postgres:

    image: postgres:16

    environment:

      POSTGRES_DB: platform

      POSTGRES_PASSWORD: ${DB_PASSWORD}

    volumes:

      - ./pgdata:/var/lib/postgresql/data

minio:

    image: minio/minio

    command: server /data --console-address ":9001"

    environment:

      MINIO_ROOT_USER: ${MINIO_USER}

      MINIO_ROOT_PASSWORD: ${MINIO_PASSWORD}

    volumes:

      - /mnt/nas-media:/data

api:

    build: ./spring-app

    depends_on: [postgres, minio]

    ports:

      - "8080:8080"
AWS 이전 전략 (수익성 확인 후)
MinIO → AWS S3 (endpoint만 교체, 코드 변경 거의 없음)
Postgres → RDS (pg_dump → restore)
미니PC → EC2/ECS (Docker 이미지 그대로 배포)
7. 보안 / 운영 체크리스트
   업로드 파일: 확장자만이 아닌 실제 파일 시그니처 검사, 용량 제한, 악성 파일 스캔
   CUSTOMER 입력 텍스트: XSS 방지를 위한 sanitize 필수 (React 기본 텍스트 렌더링만 사용, innerHTML 금지)
   개발자 CREATOR가 등록하는 컴포넌트 코드: 최소한의 코드 리뷰/승인 프로세스
   DB 정기 오프사이트 백업 (NAS RAID는 하드웨어 고장만 방어, 논리적 삭제/랜섬웨어엔 무력)
   개인정보처리방침 필요 (사진, 이름, 날짜 등 개인정보 다룰 경우)
   가정용 인프라 특성상 고려할 것: 업로드 대역폭(비대칭 회선), UPS(정전 대비), 트래픽 스파이크 대비 → 장기적으로는 AWS 이전으로 해소
8. 단계별 로드맵
   단계
   내용
   0단계
   미니PC Docker Compose 세팅, NAS NFS 마운트, Cloudflare Tunnel 연결
   1단계 (MVP)
   MASTER가 직접 핵심 컴포넌트 3~5개 제작 (반응형 + platformMode 적용) + CUSTOMER 사이트 에디터(순서 배치·텍스트/이미지 교체·발행) 완성 → 지인 대상 배포 후 반응 확인
   2단계
   CREATOR용 코드 SDK 문서화, 컴포넌트 등록 프로세스 오픈
   3단계
   보안 체크리스트 정식 적용 (업로드 검증, 백업 자동화, 개인정보처리방침)
   4단계
   노코드 CREATOR 빌더 (스키마 기반 폼 자동 생성)
   5단계
   트래픽/수익 확인 후 AWS로 인프라 확장 이전
