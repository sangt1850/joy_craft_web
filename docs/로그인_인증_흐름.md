# JoyCraft 로그인/인증 흐름

작성일: 2026-09-03

이 문서는 현재 JoyCraft의 로그인 유지 방식과 API/웹 클라이언트 인증 흐름을 정리한다. 현재 구조는 짧은 Access Token과 HttpOnly Refresh Token을 함께 쓰는 방식이다.

## 전체 구조

JoyCraft는 인증 상태를 두 종류의 토큰으로 관리한다.

| 구분 | 저장 위치 | 기본 만료 | 용도 |
| --- | --- | ---: | --- |
| Access Token | 브라우저 `localStorage` | 30분 | 일반 API 요청의 `Authorization: Bearer` 헤더 |
| Refresh Token | 브라우저 HttpOnly 쿠키 `refresh_token` | 7일 | Access Token 재발급 및 로그인 유지 |

Access Token은 프론트 JavaScript에서 읽고 API 요청 헤더에 붙인다. Refresh Token은 HttpOnly 쿠키라서 JavaScript에서 직접 읽을 수 없고, 브라우저가 API 요청 시 자동으로 함께 보낸다.

서버는 Refresh Token 원문을 DB에 저장하지 않는다. `user_sessions.refresh_token_hash`에 SHA-256 해시만 저장하고, 쿠키로 들어온 Refresh Token을 해시해 DB 값과 비교한다.

## 서버 저장 구조

API 프로젝트 기준 주요 파일:

| 파일 | 역할 |
| --- | --- |
| `global/session/UserSession.java` | 사용자별 서버 세션 엔티티 |
| `global/session/UserSessionRepository.java` | 세션 조회. refresh token hash로 조회 가능 |
| `global/cache/SessionCacheService.java` | 세션 저장, 검증, 만료 연장, refresh token 생성/해시 |
| `global/jwt/JwtProvider.java` | Access Token 발급/검증 |
| `global/jwt/JwtFilter.java` | API 요청마다 Access Token 검증, 세션 검증, 토큰 연장 |
| `user/service/AuthService.java` | ID/PW 로그인, 회원가입, 강제 로그인, refresh, logout 처리 |
| `user/service/KakaoAuthService.java` | 카카오 로그인/가입 후 토큰 발급 |
| `user/controller/AuthController.java` | 인증 API와 refresh cookie 설정 |

`user_sessions` 테이블은 다음 정보를 갖는다.

| 컬럼 | 의미 |
| --- | --- |
| `user_id` | 사용자 ID. 세션 PK |
| `session_id` | Access Token의 `sid` claim과 비교하는 세션 ID |
| `refresh_token_hash` | Refresh Token SHA-256 해시 |
| `expires_at` | 로그인 유지 만료 시각 |
| `last_refreshed_at` | 마지막 세션 연장 시각 |

`refresh_token_hash` 컬럼은 `V20__add_refresh_token_hash_to_user_sessions.sql` 마이그레이션에서 추가된다.

## 설정값

API `application.yaml`의 인증 관련 기본값:

```yaml
jwt:
  access-token-expiry-minutes: ${JOYCRAFT_JWT_ACCESS_TOKEN_EXPIRY_MINUTES:30}

auth:
  refresh-cookie-secure: ${JOYCRAFT_REFRESH_COOKIE_SECURE:false}

session:
  ttl-days: ${JOYCRAFT_SESSION_TTL_DAYS:7}
  pre-auth-ticket-ttl-minutes: ${JOYCRAFT_PRE_AUTH_TICKET_TTL_MINUTES:2}
```

운영 HTTPS 환경에서는 `JOYCRAFT_REFRESH_COOKIE_SECURE=true`로 두는 것이 맞다. 로컬 HTTP 개발 환경에서는 Secure 쿠키가 저장되지 않을 수 있으므로 기본값은 `false`다.

## 로그인 흐름

### 1. ID/PW 로그인

프론트가 다음 API를 호출한다.

```http
POST /api/auth/login
Content-Type: application/json

{
  "loginId": "...",
  "password": "..."
}
```

서버 처리:

1. `AuthService.login()`이 계정과 비밀번호를 검증한다.
2. 이미 유효한 세션이 있으면 새 토큰을 바로 발급하지 않고 `alreadyLogin=true`, `preAuthTicket`을 반환한다.
3. 기존 세션이 없으면 새 `sessionId`와 새 Refresh Token을 생성한다.
4. Refresh Token은 SHA-256 해시로 DB에 저장한다.
5. Access Token을 발급한다. Access Token에는 사용자 ID와 `sid` claim이 들어간다.
6. 응답 body에는 Access Token을 넣고, 응답 cookie에는 HttpOnly Refresh Token을 넣는다.

응답 예:

```http
HTTP/1.1 200 OK
Set-Cookie: refresh_token=...; Path=/; Max-Age=604800; HttpOnly; SameSite=Lax

{
  "data": {
    "accessToken": "..."
  }
}
```

프론트는 `data.accessToken`을 `localStorage.accessToken`에 저장한다. Refresh Token은 HttpOnly 쿠키라 JS 코드에서 직접 저장하지 않는다.

### 2. 중복 로그인 감지와 강제 로그인

같은 사용자의 기존 세션이 살아 있으면 `/login`은 다음 형태를 반환한다.

```json
{
  "data": {
    "alreadyLogin": true,
    "preAuthTicket": "..."
  }
}
```

프론트는 사용자 확인 후 다음 API를 호출할 수 있다.

```http
POST /api/auth/force-login
```

서버는 preAuthTicket을 검증하고 기존 세션을 삭제한 뒤 새 세션, 새 Access Token, 새 Refresh Token을 발급한다.

### 3. 카카오 로그인

카카오 로그인도 최종적으로 같은 세션 구조를 사용한다.

1. `/api/auth/kakao/url`에서 서버 발급 OAuth state와 카카오 인가 URL을 받는다.
2. 프론트는 state를 `sessionStorage`에 보관하고 카카오 인가 페이지로 이동한다.
3. 콜백에서 `/api/auth/kakao/callback`을 호출한다.
4. 기존 카카오 사용자면 Access Token + Refresh Cookie를 발급한다.
5. 신규 사용자면 `registerToken`을 반환하고, 닉네임 등록 후 `/api/auth/kakao/register`에서 토큰을 발급한다.

## 일반 API 요청 흐름

프론트 공통 클라이언트 `src/api/client.ts`가 모든 인증 API 요청에 Access Token을 붙인다.

```http
Authorization: Bearer <accessToken>
Cookie: refresh_token=<httpOnly-cookie>
```

서버 `JwtFilter` 처리:

1. Authorization 헤더에서 Access Token을 읽는다.
2. JWT 서명과 만료를 검증한다.
3. JWT subject에서 `userId`, claim에서 `sid`를 읽는다.
4. `SessionCacheService.get(userId)`로 서버 세션을 찾는다.
5. 서버 세션이 없으면 `SESSION_EXPIRED`로 401 응답한다.
6. 서버 세션의 `sessionId`와 JWT의 `sid`가 다르면 `SESSION_REPLACED`로 401 응답한다.
7. 인증 성공 시 `SecurityContext`에 사용자 ID를 넣는다.
8. 세션 만료 시간을 현재 시각 기준 7일로 다시 연장한다.
9. 응답 헤더 `X-Access-Token`에 새 Access Token을 내려준다.
10. 요청 쿠키의 Refresh Token이 현재 세션과 일치하면 refresh cookie의 `Max-Age`도 다시 7일로 연장한다.

즉 사용자가 계속 API를 사용하면 서버 세션, Refresh Cookie, Access Token이 함께 갱신되어 로그인 상태가 유지된다.

## Access Token 자동 재발급

Access Token이 만료되면 일반 API 요청은 401을 받을 수 있다.

프론트 `src/api/client.ts`는 인증 API 요청에서 401이 발생하면 한 번만 다음 API를 호출한다.

```http
POST /api/auth/refresh
Cookie: refresh_token=<httpOnly-cookie>
```

서버 처리:

1. `AuthController.refresh()`가 쿠키에서 `refresh_token`을 읽는다.
2. `AuthService.refresh()`가 refresh token hash로 DB 세션을 찾는다.
3. 세션이 만료되지 않았으면 세션 만료 시간을 다시 7일로 연장한다.
4. 기존 `sessionId`로 새 Access Token을 발급한다.
5. 같은 Refresh Token을 다시 HttpOnly 쿠키로 내려주며 `Max-Age`를 7일로 갱신한다.

프론트는 refresh 성공 시 새 Access Token을 `localStorage`에 저장하고, 원래 실패했던 API 요청을 한 번 재시도한다.

동시 요청에서 여러 API가 동시에 401을 받아도 `refreshPromise`를 공유하므로 `/auth/refresh`는 한 번만 호출된다.

## 새로고침/재방문 로그인 복구

브라우저 새로고침 또는 재방문 시 다음 두 경우가 있다.

### Access Token이 localStorage에 남아 있는 경우

`AuthGuard` 또는 `LandingPage`가 `authStore.fetchMe()`를 호출한다. `/api/auth/me`가 성공하면 로그인 상태를 복구한다.

### Access Token은 없고 Refresh Cookie만 남아 있는 경우

`authStore.fetchMe()`는 먼저 `refreshAccessToken()`을 호출한다.

1. `/api/auth/refresh` 요청
2. refresh cookie 검증
3. 새 Access Token 발급
4. `localStorage.accessToken` 저장
5. `/api/auth/me` 호출
6. 사용자 정보 저장 및 로그인 상태 복구

이 흐름 때문에 `/` 랜딩 페이지에 접근해도 refresh cookie가 유효하면 랜딩을 보여주지 않고 바로 `/dashboard`로 이동한다.

## 랜딩 페이지 리다이렉트

`src/pages/public/LandingPage.tsx`는 mount 시 `fetchMe()`를 호출한다.

- 인증 확인 중이면 로딩 화면을 보여준다.
- 인증 성공이면 `<Navigate to="/dashboard" replace />`로 이동한다.
- 인증 실패면 랜딩 페이지를 그대로 보여준다.

따라서 로그인된 사용자가 `/`로 접근하면 랜딩 페이지가 아니라 대시보드로 이동한다.

## 로그아웃

프론트는 `src/api/auth.ts`의 `logout()`을 통해 항상 `/api/auth/logout`을 호출한다. Access Token이 없어도 refresh cookie는 JS에서 읽을 수 없기 때문에 서버에 로그아웃 요청을 보내야 한다.

서버 처리:

1. 인증 principal이 있으면 해당 사용자 세션을 삭제한다.
2. principal이 없어도 refresh cookie가 있으면 refresh token hash로 세션을 찾아 삭제한다.
3. `Set-Cookie: refresh_token=; Max-Age=0`으로 브라우저 쿠키를 만료시킨다.
4. 프론트는 `localStorage.accessToken`을 삭제하고 로그인 상태를 초기화한다.

## 보안 특성

현재 방식의 장점:

- Refresh Token은 HttpOnly 쿠키라 일반 JavaScript에서 읽을 수 없다.
- Access Token은 짧게 유지한다.
- 서버 DB 세션이 있으므로 로그아웃/강제 로그인 시 즉시 무효화할 수 있다.
- Refresh Token 원문은 DB에 저장하지 않고 해시만 저장한다.
- API 사용이 계속되면 로그인 유지 기간이 7일로 다시 연장된다.

주의할 점:

- 운영 HTTPS 환경에서는 반드시 `JOYCRAFT_REFRESH_COOKIE_SECURE=true`가 필요하다.
- SameSite는 현재 `Lax`다. 완전한 same-site 배포 구조라면 `Strict`도 검토할 수 있다.
- Access Token은 여전히 `localStorage`에 있으므로 XSS 방어가 중요하다.
- Refresh Token 탈취 대응을 강화하려면 refresh token rotation을 추가할 수 있다. 현재는 같은 Refresh Token의 만료 시간을 연장하는 방식이다.

## 관련 엔드포인트 요약

| Method | Path | 인증 | 설명 |
| --- | --- | --- | --- |
| `POST` | `/api/auth/login` | 공개 | ID/PW 로그인 |
| `POST` | `/api/auth/force-login` | 공개 | 기존 세션 제거 후 강제 로그인 |
| `POST` | `/api/auth/register` | 공개 | 회원가입 후 로그인 |
| `POST` | `/api/auth/refresh` | Refresh Cookie | Access Token 재발급 |
| `POST` | `/api/auth/logout` | Access Token 또는 Refresh Cookie | 서버 세션 삭제 및 쿠키 만료 |
| `GET` | `/api/auth/me` | Access Token | 현재 사용자 조회 |
| `GET` | `/api/auth/kakao/url` | 공개 | 카카오 인가 URL/state 발급 |
| `POST` | `/api/auth/kakao/callback` | 공개 | 카카오 콜백 처리 |
| `POST` | `/api/auth/kakao/register` | registerToken | 카카오 신규 사용자 닉네임 등록 |
